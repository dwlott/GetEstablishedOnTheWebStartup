# Quick Startup Walkthrough

This is the shared interview protocol for the product's reusable startup
instructions and the Startup package. The active repository's own identity,
goals, permissions, and available Capabilities still govern the work.

## Reusable source and maintained copy

The canonical reusable Markdown source is
`C:\Repositories\GetEstablishedOnTheWeb\Capabilities\GettingStarted`.
The maintained package copy is the same relative folder in
`C:\Repositories\GetEstablishedOnTheWebStartup`. Update the product source
and apply reviewed guidance to Startup together. Preserve each repository's
identity, goal references, and available modules. Keep real project answers
in the project's owner registers, never in either reusable guidance copy.

## Orient and resume

Read owner registers, the backlog, and `Workspace/QuickStartupProgress.md`
when it exists. Record adoption confirmation already supplied; do not ask
again. A completed interview uses its existing goals and next task. A partial
interview resumes at its first pending question. Preserve answers and skips.
If no checkpoint exists, reconstruct covered questions from supplied facts
and the owner registers instead of repeating the interview.

After root classification, create the checkpoint below in the existing
`Workspace/` folder for an authorized startup in an adopted project. Do not
create a real interview record or reset owner registers in either canonical
repository while editing or packaging instructions. Without write access,
maintain a compact copy-ready checkpoint in chat and state that it is unsaved.

## Ask, capture, and advance

1. Show [QuickStartupGreeting.md](QuickStartupGreeting.md)'s opening and five
   questions once. Populate known answers first. Question 1 distinguishes a
   new venture, an existing website, or other work without a separate interview.
2. Ask only the first pending question, labelled **Question N of 5 — topic**.
   Use one question in a supported question tool when available, or ask in chat.
   Wait for a real reply. A timeout or silence is not an answer or permission.
3. Accept brief answers, fuller answers, or explicit skips/deferrals. One
   concrete outcome is sufficient; do not manufacture extra goals to reach a
   quota. Use an answer for every question it covers.
4. Acknowledge briefly. Save the factual summary and question status before
   asking the next. Update `OwnerGoals.md` and `OwnerPreferences.md` with supplied
   facts as they arrive, preserving existing entries. The checkpoint tracks
   interview progress; those registers remain authoritative for durable facts.
5. At question 4, inspect the accessible environment read-only and ask only
   about details that matter and remain unknown. The environment question bank
   is a reference, not another questionnaire. Store relevant device/profile
   facts in `OwnerPreferences.md`; update `OwnerEnvironment.md` only if that
   register exists or a profile-aware capture needs it.
6. Lead into the next question without requiring "next" or a pasted question.
   If the owner asks to stop, save progress, say which question is next, and
   stop. Never mark remaining questions answered merely to finish startup.
7. Once the five questions are covered or explicitly deferred, use the short
   existing-site follow-up when applicable, then offer useful optional setup
   and complete identity verification. If all goals were deferred, record
   orientation complete with the next outcome still undecided; do not invent
   a task or claim the owner's project goal has been achieved.

## Checkpoint scaffold

Copy only into an authorized project interview. Fill values from evidence.
Keep credentials, personal contact details, and private attachment text out.

```markdown
# Quick Startup Progress

Updated: <date>
Interview state: In progress / Questions covered / Complete
Project direction: <new venture / existing website / other / unknown>
Next prompt: <question number and topic, follow-up, optional choice, or none>

| Question | Status | Answer summary / authoritative record |
| --- | --- | --- |
| 1 — project | Pending | |
| 2 — outcome | Pending | |
| 3 — priority | Pending | |
| 4 — tools | Pending | |
| 5 — prior material | Pending | |

Use Pending, Answered, Skipped, or Deferred. Record only actual owner decisions.

Maintenance follow-up: <not applicable / pending fields / covered; preferences link>
Indexing: <Not offered / Awaiting answer / Accepted / Deferred / Declined / Already set up>
Reference review: <Not needed / Not offered / Awaiting answer / Accepted / Deferred / Declined>
GitHub: <Not requested / Requested; preferences link>
Identity verification: <Pending / Passed / Not applicable; evidence>
Next action: <concrete task, or undecided>
```

When returning, recheck paths and permissions before actions. Mark Complete
only after capture, optional-choice handling, required adopted identity checks,
and the owner-facing close. A saved checkpoint is not permission for a site
write, import, production action, commit, or push.

## Optional choices without friction

- **GitHub:** retain the current Git state and wait until requested. Do not ask
  the owner to pick a remote during startup unless connecting GitHub is their
  stated task.
- **Indexing:** reuse a recorded preference. Otherwise offer once, with its
  benefit: "Would you like a small directory of project notes so future
  sessions can find them quickly?" Create missing indexes only after acceptance.
- **References:** suggest links only when useful to the actual goal. Reviewing
  them is optional; do not require a quota of URLs or a separate research pass.
- Present at most one optional decision at a time, after the core interview.
  An unanswered offer stays Awaiting answer. If the owner continues with work,
  leave it unresolved and proceed without the optional action; do not label it
  declined or deferred unless the owner says so. Optional setup does not block
  a clear next task or require another round of permission for authorized work.
